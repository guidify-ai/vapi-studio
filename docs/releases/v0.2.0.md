# Vapi Studio 0.2.0 — Pure intentions, decision-model scanning, app-owned decisions

- **Status:** Released 2026-10-25 — signed off on the roofing project built on Studio ([ARD-0005](../ards/ARD-0005-release-flow.md))
- **Previous published version:** 0.1.2 (0.1.3 was merged but never published; its contents ship here)
- **Breaking:** yes — see [Upgrade guide](#upgrade-guide)

## Where we were

After 0.1.2, Studio routed a caller's turn in three tiers: code matchers, the
node's own regex resolver, then an LLM "Brain" that wrote JSON scores for
intention *names*. The framework quietly made product decisions for every app:
which models were allowed and what they cost, a default model, the English line
a caller heard when a call ran long, the country of an SMS number, the maximum
length of a call. Releases went to npm when the code looked right; the projects
built on Studio were still on 0.1.1.

Two events broke those assumptions in the same month. OpenAI retired Studio's
default model, so every app that relied on the default failed every scan. And
0.1.2's correct routing fix silently broke one of the projects built on Studio — found only
while preparing this release. 0.2.0 is the answer to both: the app owns its
decisions, the framework owns the mechanism, and nothing ships without real
calls.

## Announcement

Vapi Studio 0.2.0 makes **intentions pure: an intention is a direction, not a
data grab.** A scan now answers one question — where does the call go next —
and the Node that receives the answer reads, checks and, if needed, re-asks for
the data itself. Since 0.0.1 one scan did both jobs, so a single timeout lost
the route and the caller's answer together; now each part has one job, and
"why did the call go there?" is answered by the intention alone. The same idea
reaches portals: when a caller declines a detour ("okay, I'll stay with you"),
the call returns to the question it was on and asks it again, instead of
treating that agreement as an answer.

Pure intentions also open the door to **decision models**. Besides LLM
scanning, Studio can now score intentions with OpenAI Decisions and TypeSafe
Jev (experimental), which answer "does the caller mean X?" with a probability,
bill input tokens only, and are built for low latency. Every intention now
carries a one-sentence description, and the scanner sees what the call has
collected so far, so routing rests on meaning and context rather than on
intention names.

0.2.0 also hands decisions back to your app. Studio no longer ships a list of
"supported" models, a default model, prices, English lines your callers hear, or
a hidden phone-number country. You pick the Brain adapter and model, write your
own goodbye and SMS text, and tune timeouts that used to be fixed.

Upgrading from 0.1.x is a short checklist: a few `forRoot` settings are now
required. Apps that pin `@guidify-ai/vapi-studio` should read the upgrade guide
before bumping.

## Features

### 1. Decision-model Brain drivers

**What:** Two new Brain adapters. `OpenAiDecisionsBrainAdapter` calls OpenAI's
`/v1/decisions` (e.g. `gpt-6-luna`); `TypeSafeJevBrainAdapter` calls TypeSafe's
`/v1/systemone` (e.g. `jev-latest`). A scan asks one yes/no question per
candidate intention and gets an independent probability for each, rounded to
6 decimals, which then follows the usual threshold → `studio.isUnknownTransition`
rules. Decision models cannot write text, so Nodes' `clarify` and `judge`
calls go to a chat model you name in `brain.llm`.

**Why:** Picking an intention is a classification problem. A chat LLM solves it
by *writing* JSON scores: you pay for output tokens, wait for generation, and
get whatever numbers the model chose to type. A decision model answers the
classification question directly. Both providers bill input tokens only (as
listed in October 2026: OpenAI Decisions $0.10 per million input tokens,
TypeSafe Jev $0.042 per million), so a scan costs less than the same context
sent to an LLM, and both are positioned for live-call latency — the thing a
voice agent cannot spend. Two drivers instead of one because they price and
perform differently, and an app should be able to switch with one line.
One job per model: the decision model scores, the chat model writes.

**Trade-offs:** Apps on a decision driver configure two providers (scanner and
`brain.llm`). Scores are independent, not a distribution — several
intentions can clear the threshold; the Supervisor's priority walk already
handles that. Only OpenAI Decisions is exercised in sign-off; Jev ships
**experimental**, tested against recorded request/response shapes only, and
loses the label once it has run on real calls.

**Reference:** [ARD-0006](../ards/ARD-0006-decision-brain-drivers.md),
[Runtime API — Brain](../reference/runtime-api.md).

### 2. Intention descriptions, memory and pre-ranking in every scan

**What:**
- **Descriptions.** Every intention can carry a one-sentence meaning: on a listen
  intention, on a `CodeIntention` (`description`), or in a new top-level
  `intentions:` map in `flow.yaml`. Built-in `studio.*` intentions have framework
  descriptions. Decision drivers **require** one for every candidate: a missing
  description logs an error and the turn goes to the unknown transition.
- **Memory.** The scanner receives the call's collected memory by default —
  including caller details such as name, phone or email, which then leave your
  app for the provider. `brain.memorySnapshot` lets the app trim or redact it
  first; Studio does not redact on its own, because what counts as sensitive is
  the app's call.
- **Pre-ranking.** Regex and match-phase intentions still run first and route
  without a scan when confident. When the scan runs, it gets `priors`: the
  current step's expected intentions with their boosts, and match-phase scores
  that fired below the threshold.

All three reach LLM scans too.

**Why:** `isAcceptedOffer` means little to a model that has not seen the flow;
"the caller accepts the offer the assistant just made" does.
A per-question probability model needs the meaning stated, so for decision
drivers a missing description is treated as an app bug and fails loudly instead
of producing confident nonsense. Memory matters because the right answer often
depends on what is already known ("yes" means different things before and after
the address is collected). Pre-ranking matters because deterministic matchers
are cheap, exact and written by the people who know the flow — throwing away a
matcher's 0.35 "probably this" wastes signal, while letting it decide would
override what the caller actually said, so it is passed as a weak hint.

**Trade-offs:** Apps moving to a decision driver must describe every intention.
Memory leaves the process by default — the app decides what to redact
(we chose "send by default, hook to trim" so routing quality does not depend on
remembering to opt in). Larger memory means larger requests.

**Reference:** ARD-0006, [Flow schema — intentions](../reference/flow-schema.md).

### 3. Pure intentions: the scan routes, the next Node extracts

**What:** An intention answers one question: where does the call go next. Every
Brain scan now returns ranked intentions only. The Node that handles the answer
reads `ctx.userText` itself — in `before()`, `run()` or a helper, with code,
regex, direct use or `ctx.clarify` — triages the value and asks follow-ups. Data
that breaks the Node's expectations is an error: `catch()` now handles errors
from `before()` as well as `run()`, and can route back so the asking Node
re-asks, rephrased for the failure. `sayAndListen({ extract })` and
`onExtracted` are removed; `brain.delegate` is renamed `brain.llm`. One call to
action per Node is recommended, not enforced.

Portals follow the same rule. When a caller agrees to leave a portal ("okay,
I'll stay" after a talk-to-human re-engage, "yes, still here" after a
still-there check), `isContinue` is a direction back to the origin Node — so
Studio restores the origin and repeats its question (the `sayAndListen` text,
now kept on the listen as `listen.question`) instead of re-scanning the
agreement against the origin. The origin's `run()` is not re-executed.

**Why:** Since 0.0.1 one scan did two jobs: decide where to go, and pull values
out of the answer for fields the *asking* Node declared on behalf of the next
one. A real call showed the cost — a timed-out scan lost the route and the
phone number together. Decision models made it worse: they cannot write, so
keeping extraction meant a second chat-model call alongside every scan, while
most callbacks were already parsing the raw text themselves. Treating a Node's
expectations like a method signature puts triage where the knowledge is, and
"where did the call go" becomes explainable from the intention alone. The
portal change came from the same thinking and a test that failed: a caller
asked for a person while the assistant was reading back a phone number, agreed
to stay, and the replayed "okay, sure" confirmed the number — the call moved on
and texted a form.

**Trade-offs:** Breaking for apps that used `extract`: each field moves into
the Node that handles the answer. A Node that needs a chat model to read messy
input (spelled emails, addresses) calls it after the scan, not alongside it.
Nodes with a custom `catch()` now also receive `before()` errors. When a caller
declines a portal and adds an answer in the same breath ("no thanks, my number
is 555…"), the answer is kept only if the portal's listen offers that
intention; otherwise the origin re-asks and the caller repeats.

**Reference:** [ARD-0008](../ards/ARD-0008-pure-intentions.md),
[Runtime API — Listen](../reference/runtime-api.md).

### 4. Model-agnostic Brain

**What:** The stock LLM adapters (OpenAI, Anthropic, Google, xAI) no longer
contain model whitelists, a default model, or price tables. `brain.model` is
required and passed through unchanged. `brain.providerOptions` is merged into
the provider request (Studio sends no sampling settings of its own). Studio
reports token usage only.

**Why:** OpenAI retired `gpt-4.1-nano` — Studio's default — while it was still
whitelisted, so every app without an explicit model failed every scan. Its
successor `gpt-6-luna` rejects `temperature: 0`, so simply adding it to the list
would have failed every scan too. Changing models required a Studio release and
an npm publish. Which model an app uses is an application decision, like its
flow or its copy; provider catalogues and prices are remote facts that go stale
the day they are copied.

**Trade-offs:** Apps must name a model and own its settings. Studio no longer
estimates cost — the provider's bill is the source of truth.

**Reference:** [ARD-0003](../ards/ARD-0003-model-agnostic-brain.md).

### 5. Framework decision boundary

**What:** One rule for which decisions Studio may make: **invariants** (safety,
correctness, Vapi protocol) are the framework's; **mechanism tuning** may have a
framework default only if the app can override it; **app content** (anything a
caller hears or reads, language, country, vocabulary, provider and model) and
**remote facts** (prices, catalogues, limits) are never the framework's. An audit
against that rule changed:

| Change | Reason |
| --- | --- |
| `brainAdapter` required (no silent mock) | An app that forgot it ran a mock Brain in production without noticing |
| `limits.endMessage` required | The default goodbye was Studio's English in your caller's ear |
| Turn / duration ceilings removed (defaults 40 turns / 20 min stay; limits cannot be disabled) | 150 turns / 60 min was a number Studio picked for someone else's product |
| Listen timeout ceiling removed (Vapi's 0.4 s floor stays) | Long dictation (addresses) needs more than 12 s; the floor is Vapi's rule |
| `brain.timeoutMs` (default 3000) | 3 s was hardcoded; slower models or tighter call budgets need their own |
| SMS phone numbers E.164 only | Ten digits → `+1` silently assumed North America |
| SMS `disposeContext.body` required, `{formUrl}` placeholder | The default text was Studio's English |
| Form page title / `lang` options | Opt-in helper strings must all be options |
| Business words removed from mock name extractor | One customer's business vocabulary lived in the framework |

**Why:** ARD-0003 showed that facts frozen into the framework go stale. The audit
found the same pattern beyond models — copy, country, ceilings — and each one
either broke an app silently or forced a Studio release for an app-level change.
A written boundary turns "should Studio decide this?" from a debate into a table
lookup for every future PR.

**Trade-offs:** Breaking: apps must supply what Studio used to assume. Kept
deliberately (with reasons in ARD-0004): limits always on, loop guards,
prompt-injection guard, Vapi tool-name defaults, internal prompt sizes, English
Brain system prompts (never spoken to callers).

**Reference:** [ARD-0004](../ards/ARD-0004-framework-decision-boundary.md).

### 6. Patched Node runtime adopted end to end

**What:** Studio requires Node `^22.23.4 || ^24.22.1 || >=26.12.1`. The floor
was published in 0.1.2; 0.2.0 is the release the projects built on Studio, their Docker
images and the verification pipeline run on Node 24.22.1.

**Why:** The October 2026 Node security release fixed vulnerabilities in the
runtime every Studio app runs on, and a voice agent is an internet-facing
service handling caller data. An `engines` floor in the package is necessary but
not sufficient: the maintainer-owned apps stayed on 0.1.1 and older Node, so the
fix only counts once the apps and their images actually move — which this
release's flow now enforces (feature 8).

**Trade-offs:** Hosts on older Node fail `yarn install` (engines check);
developers must upgrade their local Node, not only containers.

**Reference:** PR #4, [Installation](../getting-started/installation.md).

### 7. Vapi-only North Star

**What:** Written product scope: Studio is a toolkit for building on Vapi.
Making Vapi optional or swappable is a non-goal; adapters are a cleanliness
boundary, not a provider seam; "channel" means a surface of a Vapi conversation.
Recorded at the top of the constitution and in ARD-0002.

**Why:** Neutral words in the code ("channel", "provider ingress") read like a
platform-agnostic engine and invited proposals the project would never merge.
A written north star is a contribution filter and lets features use Vapi
directly instead of through a lowest-common-denominator abstraction.

**Trade-offs:** None for apps; contributors lose the "generic engine" option on
purpose.

**Reference:** [ARD-0002](../ards/ARD-0002-vapi-only-north-star.md).

### 8. Release flow with mandatory sign-off

**What:** A version moves through five gated stages: `develop` holds the next
version and is never published; the projects built on Studio switch to the
local checkout and adapt; the maintainer signs off with real calls on them; then
`develop` → `master`, tag, npm publish; then the projects switch to the exact
published version immediately. **No exceptions** — patch and hotfix releases
need the same sign-off, and any new runtime path (in 0.2.0: OpenAI Decisions)
runs in the projects during it.

**Why:** 0.1.2 shipped a correct routing fix that broke behaviour one of the
projects relied on. Unit tests here could not catch it, the projects
stayed on 0.1.1, and the break surfaced only after the version was public — and
a published npm version cannot be changed. Only real apps on the unpublished
version, exercised with real calls, catch that class of bug in time.

**Trade-offs:** A release waits for the maintainer's calls; app repos carry
`file:` dependencies while a release is in progress.

**Reference:** [ARD-0005](../ards/ARD-0005-release-flow.md).

### 9. Release articles

**What:** This page. Every release gets one: announcement, features with
reasoning, test record, upgrade guide, reasoning check, open questions.

**Why:** Decisions were recorded one at a time (ARDs) and changes one at a time
(commits); nothing explained a version as a whole. App developers need an
upgrade checklist, the public needs plain-language notes, and spec-driven work
needs a version-by-version history of *why*. Requiring reasoning per feature
also catches changes nobody can justify before they ship.

**Trade-offs:** A little writing per feature PR.

**Reference:** [ARD-0007](../ards/ARD-0007-release-articles.md).

## How 0.2.0 was tested

- **Automated (framework):** `tsc`, `eslint`, and 151 `node:test` tests in the
  `node:24.22.1-bookworm-slim` image. Provider calls are stubbed — the default
  suite makes no paid or network calls. New in 0.2.0: request/response shape,
  refusals, missing descriptions, memory hook, `brain.llm` routing, timeouts,
  priors, and `flow.yaml` descriptions for both decision drivers; `before()`
  errors reaching `catch()` and routing back to re-ask.
- **Projects built on Studio:** they run against `develop` through
  `file:../vapi-studio`, type-check, and pass their suites in the same Node 24
  image. Each gained a guard test that fails if any intention a scan can see
  lacks a description. Upgrading them surfaced the 0.1.2 module-entry
  regression (fixed in the project) — the case ARD-0005 exists for.
- **Evals:** Studio ships an LLM-as-a-judge API (`judge`) for conversation
  evals, but no automated eval suite gates 0.2.0; sign-off is manual calls. An
  eval suite is planned for a later release.
- **Manual sign-off (2026-10-25):** the maintainer called the roofing project
  built on Studio, running **OpenAI Decisions** (`gpt-6-luna`) as the live
  scanner. The 3.4-minute call covered greeting → estimate request → SMS-form
  consent → caller-ID phone confirm → live Twilio SMS → form submitted during
  the call → read-back and confirm → triage, with Node-side extraction,
  unknown-transition recovery, and scans of about 300 ms. Issues found on that
  call were fixed afterwards and covered by tests: the goodbye looped back into
  the flow (built-in `endCall` tool, project fix), options were read as an IVR
  menu (project wording), and portal return (feature 3, found by a new test).
  The landing sample was not called: its Vapi assistant had been deleted.
- **Not tested:** the portal-return change and the endCall fix on a live call
  (tests only); the landing sample on a live call; TypeSafe Jev against the live API (no account at release
  time); Claude, Gemini and Grok adapters live (unchanged request paths, stubbed
  tests only); squad-mode (multi-assistant) flows.

## Upgrade guide

From 0.1.x (breaking items first):

1. **Node** `^22.23.4 || ^24.22.1 || >=26.12.1` on hosts and images.
2. **`brainAdapter`** in `VapiStudioModule.forRoot` — required. Pass
   `MockBrainAdapter` explicitly for offline/dev.
3. **`brain.model`** — required for stock adapters. Drop imports of the removed
   `*-cheap-models` lists (the `Cheap*ModelId` types remain as deprecated
   `string` aliases).
4. **`brain.providerOptions`** — Studio no longer sends `temperature: 0`. Add
   it (or `reasoning_effort`, etc.) if your model takes it.
5. **`limits.endMessage`** — required; your app's goodbye line.
6. **Twilio SMS dispose** — `contactPhone` must be E.164 (normalize in the app);
   `disposeContext.body` is required, with `{formUrl}` where the link goes.
7. **Removed exports:** `HARD_MAX_CONVERSATION_TURNS`,
   `HARD_MAX_CONVERSATION_DURATION_MS`, `DEFAULT_CONVERSATION_LIMIT_MESSAGE`,
   `MAX_LISTEN_TIMEOUT_SECONDS`, `buildDefaultSmsBody`, the per-provider model
   and price lists. `resolveSmsBody` returns `null` when no body was sent.
8. **From 0.1.1 only:** module-entry turns use `studio.moduleEntry` (0.1.2).
   Nodes that checked a custom entry intention on the first visit must also
   accept it.
9. **Listen extraction removed** (ARD-0008): `sayAndListen({ extract })`,
   `onExtracted`, the `ListenExtract*` types and `BrainScanResult.extracted` are
   gone. For each field, move the parsing into the Node the answer routes to:
   read `ctx.userText` in `before()` or `run()` with your parser (or
   `ctx.clarify({ fields })` for messy input), store it in memory, and throw when
   it breaks the Node's expectations. In `catch()`, return
   `forceIntention('…')` to send the call back to the asking Node, which re-asks
   rephrased for the failure. A yes/no "field" (e.g. "number is correct") is an
   intention, not data. Custom Brain adapters return `{ intentions }` only.
10. **`catch()` now also receives `before()` errors.** Previously they broke the
    turn. A Node whose `catch()` assumed only `run()` failures should check the
    error it gets; `before()` returning `false` still means "not my turn".
11. **Portal return re-asks.** `isContinue` (and still-there "yes") no longer
    re-scans the caller's words against the origin; the origin repeats its last
    `sayAndListen` question. Tests or Nodes that expected the agreement to be
    routed as an origin answer must expect the re-ask.
12. **`brain.delegate` → `brain.llm`** — same `{ adapter, model }` shape; it now
    serves Nodes' `clarify` / `judge` only.
13. **Optional — decision drivers:** set `brainAdapter: OpenAiDecisionsBrainAdapter`
    (or `TypeSafeJevBrainAdapter`), `brain.model`, `brain.llm`
    `{ adapter, model }` (needed for `clarify` / `judge`), and describe every
    intention (`flow.yaml` `intentions:`). A guard test that checks every
    scannable intention has a description catches gaps before a call does.
14. **Optional:** `brain.timeoutMs`, form `lang` / gone-page options.
15. **Review caller data:** scans now send collected memory (name, phone,
    email, …) to the Brain provider. Set `brain.memorySnapshot` to drop or mask
    what should not leave your app.

## LinkedIn post

```text
I used to think a framework should make good decisions for you.

Vapi Studio is my NestJS toolkit for deterministic voice agents on Vapi. Until this month it shipped a list of "supported" OpenAI models, a default model, a price table, the English line your caller hears when a call runs long, and an assumption that every phone number is North American.

Then OpenAI retired the default model. Every app that trusted it failed every single turn. Fixing it meant a framework release, for what was really an app's choice.

That was the lesson behind 0.2.0: a framework owns mechanism, not decisions. I audited every choice Studio made on an app's behalf and sorted each into four classes: safety invariants (framework), tuning knobs (framework default, app override), app content (never the framework), and remote facts like prices (never copied). Everything in the last two classes left the codebase.

The other big change is how Studio decides what a caller meant. Picking an intention is a classification problem, but I solved it by asking a chat model to write JSON scores. 0.2.0 adds decision models, OpenAI Decisions and (experimental for now) TypeSafe Jev, which answer "does the caller mean X?" with a probability, bill input tokens only, and are built for low latency. Every intention now carries a one-sentence meaning, the scanner sees what the call has collected so far, and regex matchers pass along their hunches as hints instead of being thrown away.

I also made intentions pure: an intention is a direction, not a data grab. A scan used to decide where to go and pull data out of the answer in one call; when it timed out, both were lost. Now the scan only routes ("the caller gave a number"), and the next step reads and checks the number itself, asking again if it's wrong. Same for detours: if a caller asks for a human, then agrees to stay, the call goes back to the question it was on and asks it again, instead of treating "okay, sure" as an answer.

And a confession: 0.1.2 shipped a correct fix that quietly broke one of the projects built on Studio. Unit tests couldn't see it; the projects were still on the old version. So now no version reaches npm until those projects run it and I've made real phone calls. No exceptions, not even for hotfixes.

Every release now comes with an article like this one, with the reasoning behind every feature. If a feature has no reason, it doesn't ship.

Full article: https://github.com/guidify-ai/vapi-studio/blob/master/docs/releases/v0.2.0.md
```
