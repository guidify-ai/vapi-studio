# Vapi Studio 0.1.2 — Guard rails for releases and routing

- **Status:** Released 2026-10-24 — *Retrospective, written 2026-10-25 from commits*
- **Previous published version:** 0.1.1
- **Breaking:** behavioural (module-entry intention; found after release)

## Where we were

Anything could be merged into `master` and any commit could be tagged. Two
routing behaviours depended on accidents of ordering: when an intention was
listed on several nodes, the alphabetically first node won, even if the caller
was answering the current one; and a step entered through `continueTo` received
the first *answer* intention of its list, so it could act as if the caller had
already answered. Developers also kept asking which Vapi plan and phone setup
they needed. Then the October 2026 Node security release landed.

## Announcement

0.1.2 requires a patched Node (`^22.23.4 || ^24.22.1 || >=26.12.1`), fixes two
routing bugs, adds a guide to Vapi accounts and plans, and protects the release
branch: pull requests into `master` must come from `develop`, and tags must
point at `master`.

## Features

### 1. Patched Node

**What:** `engines.node` set to the patched lines; `.nvmrc` added.

**Why:** Studio apps are internet-facing services handling caller data; running
them on a runtime with published vulnerabilities is not acceptable.

**Trade-offs:** Older hosts fail install. (Apps actually moved in 0.2.0.)

### 2. Prefer the current node

**What:** When an intention maps to several nodes, the node the call is on wins.

**Why:** A caller answering "yes" to the current step's question could be routed
to a different step that listed the same intention, only because its id sorted
first.

### 3. `studio.moduleEntry`

**What:** A step entered through `continueTo` / module entry receives
`studio.moduleEntry` instead of the first intention in its list.

**Why:** That first intention was often an *answer* (a consent "yes", a phone
number), so entering a step could act on an answer the caller never gave.

**Trade-offs:** Correct, but breaking for any node that relied on the old value.
One of the projects built on Studio did, and the break went unnoticed until 0.2.0
was being prepared (after 0.1.2 was on npm), because the projects were still on
0.1.1. That miss is why 0.2.0 introduced mandatory sign-off (ARD-0005).

### 4. Vapi account & plans guide

**What:** Free vs Core plans; Vapi-provided phone numbers vs Twilio BYOK.

**Why:** It was the first question of every new app, and wrong choices only
showed up as failed calls.

### 5. Release branch protection

**What:** CI rejects PRs into `master` that don't come from `develop` and removes
tags that don't point at a `master` commit.

**Why:** A release must be one reviewed state, reproducible from its tag.

## How 0.1.2 was tested

- **Automated:** unit tests, including the routing changes.
- **Not tested:** the projects built on Studio against 0.1.2 — they stayed on 0.1.1.
  This gap let the module-entry regression reach npm.

## Upgrade guide

1. Node `^22.23.4 || ^24.22.1 || >=26.12.1`.
2. Nodes that check an entry intention on their first visit must also accept
   `studio.moduleEntry`.

## LinkedIn post

```text
Vapi Studio 0.1.2 is the release I learned the most from, mostly because of what went wrong.

On paper it was a solid patch: a required Node security upgrade, CI rules so releases only come from one reviewed branch, a guide to Vapi plans and phone numbers, and two real routing fixes. One of them stopped a caller's "yes" from being routed to the wrong step just because its name sorted first alphabetically. The other stopped steps from acting as if the caller had already answered them.

Both fixes were correct. One of them still broke one of the projects built on Studio, because it had quietly relied on the old behaviour. Unit tests couldn't see it, and the projects were still on the previous version, so nobody noticed until the version was already on npm.

A published npm version can't be fixed after the fact. That one miss reshaped how I release: since 0.2.0, no version is published until the projects built on Studio run it and I've made real calls. The bug was small. The process change was not.
```
