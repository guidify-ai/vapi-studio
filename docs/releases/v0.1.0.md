# Vapi Studio 0.1.0 — A package, not a monorepo

- **Status:** Released 2026-09-25 — *Retrospective, written 2026-10-25 from commits*
- **Previous published version:** 0.0.1
- **Breaking:** yes (apps move out of the framework repo)

## Where we were

In 0.0.1 the framework repo also held the apps: a `projects/` folder, the sample
landing app, a Makefile that orchestrated everything, and a script that
scaffolded new projects inside the repo. It worked for one developer. It did not
work as an open-source package: private product names leaked into a public repo,
every app was coupled to framework internals, and "how do I start my own bot?"
had no clean answer.

## Announcement

0.1.0 makes Vapi Studio a proper npm package. Your bot is now a separate NestJS
app that depends on `@guidify-ai/vapi-studio` — start from the public
`vapi-studio-project` starter. The release also adds a background task queue and
an in-process event bus, and documents what you need from Vapi and Twilio before
your first call.

## Features

### 1–2. npm-first; apps out of the framework repo

**What:** Apps install `@guidify-ai/vapi-studio` from npm. The `projects/`
folder, the in-repo scaffolding script, checked-in SpecKit skill copies and the
Makefile stub were removed; the sample landing app moved to its own repo; private
product names were scrubbed.

**Why:** A framework that lives in the same tree as its apps leaks app concerns
into the framework and framework internals into the apps. Publishing forces a
real public API. And a public repository cannot carry private product names.

**Trade-offs:** Framework changes now reach apps through a release (or a local
`file:` link while developing).

### 3. Task queue and event bus

**What:** `StudioTaskQueue` for background work and an in-process event bus that
apps can subscribe to.

**Why:** Voice turns must answer fast; slow work (notifications, syncs) has to
leave the turn. Observability and exports should hang off events, not be wired
into Nodes.

### 4. Host-scoped routes

**What:** Webhook at `{PUBLIC_BASE_URL}/vapi/webhook`, Custom LLM at
`{PUBLIC_BASE_URL}/vapi/chat/completions`. Recorded as ARD-0001 in 0.1.1.

**Why:** One self-hosted app has one public URL; a project UUID in the path is a
reverse-proxy concern, not the default contract.

### 5. Prerequisites documented

**What:** `.env.example` slots for Vapi and Twilio; Trust Hub (+1) and balance
guidance; a note that Vapi billing applies on top of Twilio.

**Why:** New apps failed their first call on carrier and account setup, which
the framework could not detect.

### 6. Form URLs behind UUID-routed proxies

**What:** Form POSTs default to the current path; SMS links carry the project
prefix when routed through a shared host.

**Why:** Local multi-app tunnels route by UUID prefix; links without it went
nowhere.

## How 0.1.0 was tested

- **Automated:** unit tests, mocked Brain.
- **Manual:** sample apps running against the published package.
- **Not recorded:** formal sign-off did not exist yet.

## Upgrade guide

Move your app out of the framework repo into its own NestJS project (start from
`vapi-studio-project`), depend on `@guidify-ai/vapi-studio@0.1.0`, and wire Vapi
to the host-scoped `/vapi/...` routes.

## LinkedIn post

```text
Vapi Studio 0.1.0 was mostly about deleting things.

In the first alpha, the framework repository also held my apps: a projects folder, the demo app, a Makefile that started everything, and a script that scaffolded new bots inside the repo. Convenient for me, and wrong for everyone else. App concerns leaked into the framework, framework internals leaked into the apps, private product names sat in what was about to be a public repository, and "how do I start my own bot?" had no honest answer.

So 0.1.0 split them. The framework became an npm package. Every bot is now its own NestJS app, started from a public starter repository, depending on the package like any other library. Publishing forced a real public API, which is the best design review I know.

Along the way: a background task queue so voice turns stay fast, an in-process event bus so observability hangs off events instead of being wired into steps, simple host-scoped routes for Vapi, and documentation for the account setup that was failing first calls long before any code ran.

Lesson: a framework that lives next to its apps is not a framework yet.
```
